Chat integrations let the team ask an agent questions, @-mention it in a group chat, or create issues from the chat window — without opening U Workers.

Feishu is the only IM channel enabled by default. Slack, Telegram, DingTalk, and WeCom are disabled; see [Environment variables](/environment-variables) to enable each channel independently. Existing international Lark connections remain supported.

## Default channel

| | Feishu / Lark |
|---|---|
| Installation | Generate a QR code in U Workers and authorize by scanning it with Feishu |
| DM the agent | Supported |
| Groups or channels | Triggered by @-mentioning the Bot |
| Create issues | `/issue` message command; creates the issue from your input as-is |
| Start a new Chat | `/new [message]` |
| Clear the current Chat context | `/clear [message]` |
| Connection | Platform long connection |

New connections are currently open only for mainland-China Feishu; existing international Lark connections keep working and can still be managed.

Each Bot is bound to one U Workers agent. To use several agents on the same chat platform, connect a separate Bot for each.

### Optional channels (disabled by default)

DingTalk, WeCom, and Telegram are [community-maintained](/community-maintained): they ship in every release, but carry no official support SLA. Report problems in [GitHub issues](https://github.com/multica-ai/multica/issues).

WeCom handles text messages today. Voice, image, and file messages get a short reply explaining that, and are not passed to the agent.

Telegram passes photos, files, video, and audio to the agent as attachments, and sends files the agent produces back into the chat, when the server has object storage configured; without it, media gets the same short unsupported reply as before. Stickers and other non-file messages get that reply and are not passed to the agent.

## How a message is processed

1. U Workers resolves the Bot to its workspace and agent.
2. In a group or channel, only messages that explicitly @-mention the Bot continue; DMs need no mention.
3. U Workers verifies the sender's account binding and workspace membership.
4. The message joins an [agent chat](/chat) session, and a run is created.
5. The agent's reply goes back to the original DM or thread.

Channel messages that don't @-mention the Bot never trigger the agent and are not added to its conversation context.

Ordinary messages follow this flow. `/issue` is a command, not a chat turn: U Workers posts the result back to the originating platform but does not add the command to U Workers Chat. Slack's native slash command continues through its separate asynchronous issue-creation flow.

## Conversation controls

`/new` creates a new U Workers Chat and routes later messages from that external conversation to it. `/new <message>` creates the Chat and uses the message as its first turn. The previous Chat remains stored and usable in U Workers.

`/clear` stays in the current U Workers Chat but starts a new agent-visible context. The full Chat history remains available in U Workers, while the agent cannot retrieve messages from before the boundary. `/clear <message>` uses the message as the first turn in the new context; a bare `/clear` applies to the next real message.

On Slack, `/new` and `/clear` are native slash commands in a DM. A native slash-command payload does not identify a channel thread, so use `@U Workers /new [message]` or `@U Workers /clear [message]` inside the target thread.

## Session isolation

- Feishu/Lark separates sessions by chat; later messages in the same chat continue the same session.
- Slack separates DMs by channel; in a channel, each thread holds its own session.
- DingTalk separates sessions by conversation; each DM or group continues its own session.
- WeCom separates sessions by chat; each DM or group chat continues its own session.
- Telegram separates sessions by chat; forum topics are isolated by topic.

Follow-ups in a channel still need a fresh @-mention. The agent only receives messages addressed to it — it never reads the whole channel history automatically.

## Account binding

The first time a member messages the Bot, they receive an account binding link. After signing in to U Workers, the platform account is linked to their membership in the current workspace.

U Workers only runs the agent after binding completes. Every message re-checks account binding and workspace membership; after leaving a workspace, the Bot can no longer be used to reach it.

<Callout type="info">
Account binding only confirms who the sender is. Other members on the chat platform are not automatically added to the U Workers workspace.
</Callout>

## Manage connections

Workspace owners and admins can connect or disconnect Bots; for Feishu/Lark Bots, connecting and disconnecting is also open to the agent's owner. Regular members can view connected integrations and use the agents they have access to.

After disconnecting, the Bot stops receiving new messages. Existing U Workers conversations and run records are kept.

## Self-hosting

For self-hosting, configure the encryption key for Feishu. Other channels require both their own encryption key below and the matching `FF_CHANNEL_*` switch set to `true`, followed by an API restart. Keep existing keys to reuse saved installations.

```dotenv
MULTICA_LARK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_DINGTALK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_WECOM_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_TELEGRAM_SECRET_KEY=<base64-encoded 32-byte key>
```

These keys encrypt stored Bot credentials. See [Environment variables](/environment-variables) for how to generate, store, and rotate them.

WeCom's only outbound path is the WebSocket held by one process, so what happens to a reply produced on a *different* replica depends on the realtime relay:

- **Sharded or dual relay mode** (`REDIS_URL` set — the default with Redis): the reply is forwarded to the replica holding the connection and delivered. Multi-replica WeCom is supported.
- **Legacy relay mode, or no Redis**: the reply is dropped. Run the WeCom-enabled backend as a single replica in this configuration.

In every mode, a reply produced while *no* replica holds a live connection (all mid-reconnect) is not delivered. It is counted as `multica_wecom_outbound_dropped_total{reason="no_live_connection"}` by the replica that routed it, so the size of that window is measurable; if the loss is unacceptable, a single replica remains the most conservative deployment.
