# CLAWSTA-111 — Caddy firewall prompt: diagnosis and verification

Date: 2026-11-02. Repository: `AndyTane/UWorkers-nice`, branch `agent/dsh/308d3be5b0c8` (PR #19).

## Read-only diagnosis on the desktop (`Chun-i5-12400F-32G`, 192.168.3.49)

The running portable deployment was not stopped, upgraded or reconfigured; only
queries were run over SSH.

Caddy v2.11.7, `D:\UWorkers\Portable\payload\runtime\caddy\caddy.exe`, pid 19060:

```
Get-NetTCPConnection -OwningProcess 19060 -State Listen
  ::                13443   Listen          <- wildcard, every interface (IPv4 + IPv6)
Get-NetUDPEndpoint -OwningProcess 19060
  ::                13443                   <- HTTP/3 (QUIC)
```

`https/data/Caddyfile` (generated by the old `Get-PortableCaddyfile`):

```caddyfile
{
    skip_install_trust
    admin off
    auto_https disable_redirects
    storage file_system "D:/UWorkers/Portable/https/data"
}

https://localhost:13443, https://127.0.0.1:13443, https://192.168.3.49:13443 {
    tls internal
    ...
}
```

There is no `bind` directive, so Caddy listens on the wildcard address, and
nothing turns HTTP/3 off, so it also opens UDP 13443.

Response headers show HTTP/3 being advertised:

```
curl -k -s -I https://127.0.0.1:13443/
HTTP/1.1 307 Temporary Redirect
Alt-Svc: h3=":13443"; ma=2592000
```

Firewall rules that touch 13443 (all inbound allow, no UDP rule anywhere):

| Rule | Program | Protocol | Port | Remote |
| --- | --- | --- | --- | --- |
| `UWorkers-CLAWSTA80-HTTPS-13443` | Any | TCP | 13443 | 192.168.3.0/24 |
| `UWorkers-Portable-HTTPS-13443` | `D:\UWorkers\Portable\payload\runtime\caddy\caddy.exe` | TCP | 13443 | 192.168.3.0/24 |
| `UWorkers-CLAWSTA80-Web-13001` | Any | TCP | 13001 | 192.168.3.0/24, 100.102.214.78 |

`Get-NetFirewallProfile` reports `NotifyOnListen = True` on Domain, Private and
Public. Everything else in the deployment already listens on loopback only
(postgres 16433, API 18080, web 13000).

### Why the prompt kept coming back

- The **UDP 13443 HTTP/3 socket is covered by no rule at all**. Windows Firewall
  asks before a program accepts inbound connections when no allow rule matches
  the program listen; the prompt needs an administrator click, and the person at
  the machine cannot give one, so it is dismissed and comes back on the next
  Caddy start.
- The **wildcard listen** puts the socket on every interface (Tailscale, WLAN,
  loopback), including networks the LAN-scoped rule does not admit.
- A rule that names a **different `caddy.exe` path** (moved or re-extracted
  package) stops applying; only the exact program path keeps the permission.

## What changed

- The generated Caddyfile binds `127.0.0.1` explicitly and adds the LAN address
  only when a covering rule exists; it never falls back to a wildcard.
- HTTP/3 is off (`servers { protocols h1 h2 }`), so the only 13443 listener is
  the TCP one that the rule covers.
- Install and upgrade add a program-scoped inbound rule (installed
  `caddy.exe` path, TCP 13443, LAN subnet, display name
  `UWorkers-Portable-HTTPS-<port>`) when they may; start only reads coverage and
  never changes the firewall.
- Without a covering rule the entry point stays loopback-only and the installer
  prints what that means and how to change it.

payload plus this branch's deployment scripts (v0.2.3 manifest, `-SkipInstallerBuild`):


Included checks: the installed Caddyfile binds loopback, has no wildcard bind and
disables HTTP/3; 23443 listens on 127.0.0.1 only with no UDP endpoint; the HTTPS
entry does not advertise HTTP/3; a LAN request without a firewall rule stays
loopback-only with an explanatory message and a loopback-only Caddyfile; a stale
recorded address is not bound; the packaged Caddy accepts the plan
configuration; a restart keeps the recorded plan; cleanup left no process or
port behind.

Note: the acceptance run needs PowerShell 7. Under Windows PowerShell 5.1 the
pre-existing `Get-PortableDaemonStatus` JSON parse fails on a non-ASCII device
name (this laptop's name is Chinese), which makes the daemon status check report
stopped; that predates this change and does not affect ASCII device names such
as the desktop's. Not fixed here.
