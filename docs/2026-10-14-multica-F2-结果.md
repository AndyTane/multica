## 改动与行为

- 新增独立桥命令 `multica-dsh-web`，使用当前 DSH 网页主机的工作区、会话、提示词和取消接口。它不启动另一套 DSH；网页仍控制模型、工具和 MCP。
- 每个 Multica 会话保存 DSH 会话编号，后续消息续接原会话。读取会话记录时用本次消息编号和轮次筛选，拒绝项目路径不符和已有运行的会话。投递状态不明时提示去网页检查，不自动重发。
- 将任务说明传入网页会话。网页进程的环境独立，因此通过临时 CLI 入口传递任务凭据；凭据不写入提示词，运行结束清理临时入口。
- 运行详情增加“打开 DSH 网页”和复制会话编号。后端返回兼容旧客户端的可选字段，前端丢弃异常字段和含凭据的地址。
- 配置脚本复用或创建 DSH Web 运行时配置，并固定本机桥路径。不需要数据库迁移。

## F2 收尾优化

### T2：会话记录增量读取

`server/internal/dshweb/bridge.mjs` 新增独立 `createLogReader().readNew()`，保留 `readRows(file)` 每次返回完整数组的无状态语义。完整 zstd 帧偏移、字节级半行、BigInt dev/ino、已观察大小和活动轮次一起从 prepareSession 交给轮询；续接首扫只做一次，空轮询不读文件内容。文件身份变化或大小缩小报 `session_log_replaced`。跨帧中文先拼字节再解码，修复合法 JSON 内出现替换字符的静默损坏。全量测试注入经薄适配器进入同一个轮询循环，原取消回归用例未修改。

截至 T2 提交的验证：`pnpm test:dsh-web` 20/20 通过（原 14 项加 6 项），覆盖只解析追加内容、部分帧、跨帧 JSON 与中文逐字相等、截短未完成尾帧、同长度替换、首扫交接及跨空轮询的取消保护。`git diff --check` 通过；最终版本为下表所列 25/25。

合成基准：Windows x64，Node v24.21.0，Intel Core Ultra 7 155H；50,000 行，500 个 zstd 帧，压缩后 246,506 字节。前后使用同一数据和追加序列，每次追加 10 行，每组预热 5 次、采样 40 次；写入和初始游标建立不计入轮询耗时。基线 `eecb33a23`。复现命令：`node server/internal/dshweb/bridge.bench.mjs eecb33a23`。

| 读取场景 | 改前 p50 / p95（ms） | 改后 p50 / p95（ms） |
| --- | --- | --- |
| 无新增行的单次轮询 | 212.676 / 281.886 | 0.036 / 0.088 |
| 追加 10 行后的单次轮询 | 215.253 / 267.297 | 2.139 / 2.884 |
| 续接校验的读取部分（旧两次全量，新一次首扫加空读） | 478.679 / 544.601 | 260.720 / 316.263 |

### T1：运行说明按会话去重

`bridge.mjs` 仅对 `command.system_prompt` 原文计算 SHA-256；逐轮 CLI 临时入口、取代声明和用户 prompt 不参与哈希。缓存位于用户 `.multica/dsh-web-briefs`，仅保存摘要、请求编号及字符串化的 BigInt 文件身份／大小。续接必须同时验证摘要、身份、大小和日志中的请求证据才省略说明；新会话始终发送全文。全文重新投递前使旧记录失效，日志中确认本次请求及完整投递文本后才以临时文件加改名保存，新会话也遵守这一规则。缓存写入失败时下轮重发；旧记录无法删除时停止投递并报告缓存不可用，避免留下可被误信的旧摘要。

续接需重发时附“以下运行说明取代本会话中此前的版本，按本版执行。”；逐轮 CLI 指引和用户消息照常发送。运行说明生成器已将续接、发起人和 Connected Apps 移入逐轮 prompt，本次无需修改 daemon。

验证：`pnpm test:dsh-web` 25/25 通过。新增 5 项涵盖两个独立 Node 桥进程、不同 CLI 临时路径与用户 prompt 下仍去重、说明变化及声明不影响哈希、新会话、缓存丢失／损坏／身份不符／证据缺失、投递不明时旧缓存失效，以及接收回执尚无日志证据时不写缓存。

验收风险：T1 去重从未通过带 `system_prompt` 的真实模型会话做端到端验证。本文前面的 F2 真实会话冒烟发生在本次优化之前，不能作为 T1 的端到端证明。目前证据来自单元测试及评审方对真实日志格式的核验；新增真实模型测试仍需 tane 另行授权。另一个独立风险是去重依赖 DSH 历史持续保留运行说明：即使磁盘日志仍含说明，DSH 若在模型上下文中压缩或截断历史，本桥无法保证模型仍收到该说明，本次未验证真实模型压缩行为。

### T3：从用户缓存文件启动桥

`server/cmd/multica-dsh-web/main.go` 将嵌入脚本写入 `os.UserCacheDir()/multica/dsh-web/bridge-<SHA-256 前 16 位>.mjs`，每次启动重新校验完整内容哈希。目录创建模式为 0700，Windows 用户隔离仍依赖用户缓存目录 ACL。缓存目录获取或写入失败单独报错，不回落 TempDir。脚本先写入同目录唯一文件再改名；改名失败时，已有目标内容正确则复用，否则执行本次独占文件并在子进程结束后清理。稳定缓存保留；退出码和标准输入输出透传。

入口改为 `import.meta.main`，用户参数直接通过 `node <文件> <参数>` 传递。中文和空格路径只验证路径兼容性；junction 用例才覆盖旧守卫静默退出的问题，测试同时核实 Windows junction 类型、Node 解析后的真实入口以及精确版本输出和退出码。Node 24 系列从 24.2.0 才提供该入口属性；缺失时明确返回非零并保留原 Node 错误提示，避免再次静默退出。本机为 v24.21.0。[Node 官方说明](https://nodejs.org/download/release/latest-v24.x/docs/api/esm.html#importmetamain)

使用 a2a-dsh-dispatch 技能，在核验过项目路径及工作区归属的会话中派发 T3，限定三个源代码／测试文件并禁止提交。DSH 提供候选实现及 Go 测试；我审查后要求补入口能力检查、原生 junction 清理、并发测试错误处理和缓存目录缺失测试。DSH 最后的 Node 测试因其沙箱触发权限请求，我取消了该次委派并接手验证；调度记录为 aborted，不能按 DSH 自报视作完成。我还修正了测试的临时目录隔离及 macOS HOME 隔离，独立运行最终检查后整合。
